## 1. What this is, in five sentences

This programme re-ran GRU953-Studio's own audit method against itself for a
third time (following the July 2026 eight-stage audit and several
documentation-reconciliation passes). It targeted the instruments everything
else depends on (Round 1), proved the product's cross-platform and
anti-injection promises by execution rather than by reading the code and
trusting it (Round 2), and closed the remaining drift/removal questions
(Round 3). Every fix below was reproduced by running the code before being
called a bug, and every new check was verified to have real discriminating
power — usually by deliberately breaking the code it protects and confirming
the check actually notices. Nothing here is a guess.

## 3. The three most instructive findings

### 3.1 A "fix" that was itself a regression (Round 1, Phase 1.0)

An earlier pull request had "corrected" two of `ROSTER.md`'s historical
skill-count entries (33→34, 34→35) to match today's count of 35. Checking
`git ls-tree -d` at the actual historical commits proved the *original*
numbers were correct — the real defect was a skill added later
(`devops-engineer`) that was never recorded in the changelog at all. The
"fix" had falsified two true historical statements to paper over an
unrelated gap. Reversed, and `docs-consistency.mjs` gained a rule that a
count claim inside a dated `## vX.Y.Z ...` section is a historical
statement, not a live claim, so this class of false correction can't recur.

### 3.2 A bug that survived being fixed once already (Round 2, Phase 2.4)

`verify-progress.mjs`'s structured-evidence check was fixed in Round 1,
Phase 1.3 to require all nine documented fields, not just five. Round 2's
Step 2 re-attack — deliberately trying to break that exact fix — found it
still only inspected the *first* evidence object on a "done" row. A row
narrating an old passing run followed by a failing re-run read the first
object, saw a pass, and reported clean without ever looking at the second
object's recorded failure: the same bug class the original fix was meant to
close, reopened via a different path through the same function. Fixed to
evaluate every evidence object on the row, not just the first.

### 3.3 A new safety net that broke itself twice on first contact with reality (Round 2/3)

The `hooks-crlf` CI job — real end-to-end proof that the six repo gates
tolerate a genuinely CRLF-encoded checkout — failed its own first real CI
run, for two independent reasons: its "assert the tree changed" step used
`git diff --quiet`, which `.gitattributes`' own line-ending rules make
report "no change" even when the file's real bytes are CRLF (fixed by
checking the raw bytes directly); and once that was fixed, the golden-corpus
corruption matrix's own test helper turned out to have the identical
LF-only-string-match bug the CI job exists to catch. Both were found and
fixed by rebuilding the exact CRLF tree locally and running it — not by
inspection.

## 5. Deliberately not done, and why

**The 4,932-line (now ~5,900-line) test-suite split into `hooks/test/{unit,e2e,static}/`.**
The approved plan's own Phase 3.2 named this the single riskiest change in
the whole three-round programme. Evaluated against real evidence from this
programme's own CI runs before deciding: the test suite completes in well
under a minute on Linux and macOS and around two minutes on Windows, and
because the OS legs already run as parallel CI jobs, a full pull request
already goes green in two to three minutes wall-clock. The split's own
justification — CI speed — does not reflect a real bottleneck at this
project's current scale. Manually moving ~340 tests and dozens of shared
helper functions across new files, by hand, for a file that is itself the
project's primary proof the security hooks work, was judged not worth the
risk it was explicitly flagged as carrying. Not attempted.

**A mechanical "no unexplained jargon" check (D9, comprehension).** The
product's own documented rule ("never use an acronym without expanding it
once", "no jargon, no walls of text") is a real, worthwhile discipline, but
it is fundamentally a judgement about a reader's understanding, not a
property a script can reliably detect — the genuinely user-facing text this
rule protects is mostly *runtime* chat output an AI produces during a live
session, not static prose in this repository's own files. Building a
pseudo-check against the wrong artefact would manufacture false confidence.
Disclosed rather than faked, the same standard this project already holds
its own Tier-3 (human-only) verification items to.

**Tier 2 and Tier 3 end-to-end verification (from the Round 2 plan).** A
live, interactive install-and-build session (`/plugin marketplace add`,
`/plugin install`, `/studio` on a throwaway idea), a real publish/go-public
round-trip, cloud-session container recycling with a real branch restore,
and Google Antigravity hook parity all genuinely require a human at a real
keyboard or a live GitHub round-trip — they cannot be simulated honestly.
Named here explicitly as unverified by this programme, not silently assumed
proven. A documented smoke-test script for whoever runs that session next:

1. `/plugin marketplace add GRU-953/GRU953-Studio`, then
   `/plugin install gru953-studio@gru953-studio` from a local checkout —
   confirm both commands complete without error.
2. `/studio` on a throwaway idea — confirm the warframe/Prototype gate
   blocks before any code is written, and that the per-phase plan gate
   (`phased-roadmap`) fires once per phase, not once for the whole project.
3. `/studio-status` and `/studio-dashboard` — confirm both render and match
   the actual `Dev-Memory/PROGRESS.md` state.
4. Reach an actual Publish step — confirm the confirmation pop-up appears,
   that declining it genuinely blocks the push, and that accepting it
   performs a real, private push followed by a *separate* go-public
   confirmation before any visibility change.
5. On a cloud/ephemeral session specifically: recycle the container and
   confirm the documented `memory/cloud-persist` branch restore path
   actually recovers `Dev-Memory/` on the next session start.

## 7. Convergence verdict

Not converged in the "two consecutive clean rounds" sense the approved plan
defined for early stopping — every one of the three rounds found and fixed
at least one real, live defect. The 3-round time-box (the ceiling, not the
goal) has been reached. This document is the disclosed residual register the
plan specified for that outcome, rather than a false declaration of
completeness. The pattern across rounds is the healthy one: each round found
fewer, smaller issues than the last (Round 2's dedicated re-attack pass, for
example, surfaced exactly one real bug after deliberately trying to break
every Round 1 fix) — consistent with a genuinely maturing set of checks, not
a sign that further rounds would keep finding defects at the same rate.

**What would justify a fourth round:** a new feature area not covered by
this programme's risk dimensions, a real report from the field (a user or
contributor hitting something these checks missed), or deliberately
attempting the Tier 2/3 smoke tests in §5 and finding a genuine gap. Absent
one of those, this programme's own judgement is that further rounds right
now would have diminishing returns relative to their risk and effort.

## Correction note — 2026-08-15

**The "38 agents / 35 skills" figure above (line 155) was accurate when written and is
now out of date. It is deliberately left unedited.**

A live count on 2026-08-15 gives **38 agents, 37 skills, 11 commands**. The skill count
rose by two on **2026-08-10**, after this programme concluded:

| Skill | Commit | Date |
| :-- | :-- | :-- |
| `operating-charter` | `6b96256` | 2026-08-10 |
| `openrouter-integration` | `fd56d9d` | 2026-08-10 |

Both shipped with v6.0.0, whose changelog entry names exactly these two additions
(OpenRouter support and the written operating charter). This document's sentence —
*"None added this programme"* — therefore remains **true of the programme it describes**.
The skills arrived in a later release.

(For completeness: `antigravity-integration` was renamed to
`google-antigravity-integration`, so it is not a third addition.)

**Why a note rather than an edit.** These audit files are point-in-time records. Their
figures were correct on the day, and rewriting them would falsify the record and destroy
the evidence that the roster changed at all. The project already treats such lines this
way — `ROSTER.md:166` exists precisely so a historical narrative line *"can never again be
mistaken for"* a live claim.

**No false-green gate results from this.** The counts were hardcoded once, and the
hardcoding was removed on **2026-08-10 — the same day the two skills were added**
(`hooks/hooks.test.mjs:725` records the change). Verified on 2026-08-15: no live
assertion of `35` exists in `roster-check.mjs`, `repo-integrity.mjs` or
`docs-consistency.mjs`; every remaining occurrence in the tree sits inside a comment
describing this history. The gates derive both counts from the filesystem.
