# Round 2: Cross-Perspective Synthesis & Conflict Resolution

## Major Conflicts Identified

### Conflict 1: Platform Expansion Scope
| Team | Position | Rationale |
|------|----------|-----------|
| **T2 (Architecture)** | 7 platforms in Phase 2 = **Over-scoped** | Each needs specialist, lang pack, templates, CI - unrealistic |
| **T3 (Languages)** | Need Bun/Deno/WASM **now** | Current lang packs don't support modern runtimes |
| **T6 (DX)** | Platform variety = **onboarding nightmare** | User chooses from 10+ stacks = decision paralysis |
| **T12 (Economics)** | More platforms = **more maintenance cost** | Each platform = ongoing specialist + CI + templates |

**Resolution**: **Phased platform rollout with demand validation**
- **Phase 2A (Weeks 1-4)**: Tauri v2 (desktop) + React Native/Expo (mobile) - highest user demand
- **Phase 2B (Weeks 5-8)**: Serverless/Edge (Vercel, Cloudflare Workers, Deno Deploy) - modern web default
- **Phase 2C (Weeks 9-12)**: WASI/WASM + Wails - **only if explicit user requests** (track via `ecosystem-finder`)
- **Gate**: Each phase requires **3+ user requests** or **1 paying customer** before starting
- **Architect stack menu** updated per phase with concrete defaults

### Conflict 2: Quality Gates vs. Velocity
| Team | Position | Rationale |
|------|----------|-----------|
| **T1 (Security)** | 7+ blocking gates **non-negotiable** | Regulatory compliance, supply chain security |
| **T4 (Testing)** | Add mutation/contract/property gates | Test quality unverified without them |
| **T6 (DX)** | Gates **block flow**; need **incremental + parallel** | User waits 20 min for publish = abandoned project |
| **T12 (Economics)** | Gates cost **CI minutes + API calls** | Need ROI model per gate |

**Resolution**: **Tiered, parallel, incremental gates**
| Tier | Gates (All Parallel) | Incremental Re-check |
|------|---------------------|---------------------|
| **Tiny** | Secrets, License, Progress (3) | Only changed files |
| **Standard** | + Quality, Traceability, Content (6) | Affected modules only |
| **Complex** | + Roster, Vuln Scan, AI Review (9) | Full re-run on major changes |
| **All** | **Parallel execution** (independent checks run together) | **Skip unchanged** via git diff + cache |
| **All** | **Documented skip** with risk acceptance (not bypass) | Audit trail for skipped gates |

### Conflict 3: AI Provider Explosion (10 providers)
| Team | Position | Rationale |
|------|----------|-----------|
| **T5 (AI/ML)** | 10 providers = **capability coverage** | Different strengths: Groq (speed), OpenRouter (variety), Bedrock (compliance) |
| **T12 (Economics)** | 10 providers = **cost chaos** | No unified pricing, volume discounts, regional variance |
| **T1 (Security)** | More providers = **larger attack surface** | Each API key = secret to manage, each endpoint = vuln surface |
| **T6 (DX)** | User **cannot choose** 10 providers | Decision paralysis; need **smart defaults** |

**Resolution**: **3-Tier Provider Strategy**
| Tier | Providers | Selection | User Control |
|------|-----------|-----------|--------------|
| **Default (Auto)** | Anthropic (Claude) + **1 local (Ollama)** | Router picks cheapest capable | None (just works) |
| **Opt-In Cloud** | OpenRouter (100+ models) + Groq (speed) | User enables per project | Project-level toggle |
| **Enterprise** | Bedrock, Vertex, Azure AI | Admin configures org-wide | Org policy (OPA) |
| **All** | **Unified capability registry** (not provider list) | Router queries registry | **Never** raw provider selection |

**Key**: User selects **capability** ("I need fast code generation"), not provider ("use Groq"). Router maps capability → best provider.

### Conflict 4: Tiny Tier Test Requirements
| Team | Position | Rationale |
|------|----------|-----------|
| **T4 (Testing)** | Tiny needs **min 2 tests/task** | "Working MVP" requires verification |
| **T2 (Architecture)** | Tiny = **scripts/tools**, not apps | Different quality bar appropriate |
| **T11 (User Advocate)** | Tiny users **non-technical** | Can't write tests; "does it run" is their bar |
| **T12 (Economics)** | Tests on Tiny = **diminishing returns** | 1-off script: manual verify > test suite |

**Resolution**: **Tier-Appropriate Verification** (not "testing")
| Tier | Verification Method | Evidence |
|------|---------------------|----------|
| **Tiny** | **Manual smoke test** + **1 automated check** | `verified: ./run-smoke.sh → exit 0` |
| **Standard** | **TDD** (test-first) + property-based | Structured evidence (JSON) |
| **Complex** | **+ Mutation** (80%) + **Contract** | Full evidence package |

**Tiny projects**: `tester` writes **ONE smoke test** per task (runs the app, checks output). Not unit tests. Not TDD. **Runnable verification**.

### Conflict 5: Memory System Complexity
| Team | Position | Rationale |
|------|----------|-----------|
| **T7 (Memory)** | Semantic layer + Graph DB + CRDTs | Recall accuracy, concurrent edits, scaling |
| **T2 (Architecture)** | **YAGNI** - current INDEX/GRAPH works | Premature optimization; adds deps (Ollama, Kuzu/Falkor) |
| **T12 (Economics)** | Vector DB = **cost + complexity** | Embedding API calls, storage, query latency |
| **T6 (DX)** | Memory must **stay simple** | User mental model: "files I can read" |

**Resolution**: **Progressive Enhancement** (not replacement)
| Phase | Enhancement | Trigger |
|-------|-------------|---------|
| **Current** | INDEX.md + GRAPH.md (markdown) | Baseline - works for 95% projects |
| **Phase 2** | **Local embeddings** (Ollama/nomic-embed-text) + **Tantivy** (keyword) | Project > 50 sessions OR user enables |
| **Phase 3** | **Graph DB** (Kuzu embedded) + **CRDT** (automerge) | Team > 3 users OR project > 200 sessions |
| **All** | **Fallback to markdown** always works | No hard dependency |

**Key**: Semantic layer is **opt-in enhancement**, not replacement. `memory-graph` skill updated with feature flags.

### Conflict 6: Language Pack Standardization vs. Ecosystem Reality
| Team | Position | Rationale |
|------|----------|-----------|
| **T3 (Languages)** | **Per-language baselines** in `lang-*` skills | Each ecosystem has unique best practices |
| **T2 (Architecture)** | **Unified interface** for all languages | Build Swarm, CI, cache need common contract |
| **T12 (Economics)** | **Shared tooling** where possible | `mise`/`devbox`/`nix` for env, `just`/`task` for tasks |

**Resolution**: **Dual-Layer Language Packs**
```
skills/lang-*/
├── INTERFACE.md          # REQUIRED: Common contract (build/test/lint/format/deps commands)
├── BASELINE.md           # RECOMMENDED: Idiomatic config (ruff.toml, clippy.toml, etc.)
├── templates/            # Project templates
└── ci/                   # CI snippets (GitHub Actions, GitLab CI)
```

**Contract** (`INTERFACE.md`): Machine-readable command map
```yaml
commands:
  build: "cargo build --release"
  test: "cargo nextest run"
  lint: "cargo clippy -- -D warnings"
  format: "cargo fmt --check"
  deps: "cargo deny check"
  dev_env: "mise install"  # or nix/devbox
```

**Baseline** (`BASELINE.md`): Human-readable idiomatic config (optional but recommended)

### Conflict 7: Non-Technical User Tier Questions
| Team | Position | Rationale |
|------|----------|-----------|
| **T11 (User Advocate)** | **Redesign completely** - Y/N + "I'm not sure" | Current questions use jargon ("integrations", "user data") |
| **T2 (Architecture)** | Questions **map to technical decisions** | Tier = team size + gate depth; need reliable signal |
| **T1 (Security)** | Money/PII question **must be accurate** | Regulatory liability if misclassified |

**Resolution**: **Guided Tier Interview** (not questionnaire)
```markdown
### Tier Interview Flow (interactive, interviewer-led)

Q1: "Will your app remember users between visits?"
  - Examples: "User logs in and sees their data tomorrow", "Shopping cart persists"
  - Options: [Yes] [No] [I'm not sure → interviewer explains with examples]

Q2: "Does your app handle money, passwords, or personal info (names, emails, health)?
  - Examples: "Processes payments", "Stores passwords", "Collects emails for newsletter"
  - Options: [Yes] [No] [I'm not sure → interviewer gives concrete examples]

Q3: "Will your app connect to other services like Stripe, Google Sign-in, SendGrid, or a database?"
  - Examples: "Users pay with Stripe", "Login with Google", "Send emails via SendGrid"
  - Options: [Yes - 2+] [Yes - 1] [No] [I'm not sure → interviewer maps to integrations]

→ Tier computed + explained in plain English + user can override
```

**Result**: Same technical signal, **zero jargon for user**.

### Conflict 8: Build Swarm Economics
| Team | Position | Rationale |
|------|----------|-----------|
| **T2 (Architecture)** | 2 builders **fixed** (studio skill) | Predictable, simple |
| **T12 (Economics)** | **Dynamic 1-4** based on ROI | `speedup * time_value > compute_cost` |
| **T3 (Languages)** | Some langs **don't parallelize well** (Rust incremental, Go modules) | Parallel builds can be SLOWER |
| **T4 (Testing)** | Tests **must parallelize** too | 2 builders + sequential tests = bottleneck |

**Resolution**: **Adaptive Build Swarm**
```python
def calculate_optimal_builders(task_graph, lang, time_pressure, budget_remaining):
    # Base: 1 builder
    builders = 1
    
    # +1 if: >= 3 independent tasks in graph
    if independent_tasks(task_graph) >= 3:
        builders += 1
    
    # +1 if: language parallelizes well (TS, Python, Go) AND time_pressure HIGH
    if lang in PARALLEL_FRIENDLY and time_pressure == "high":
        builders += 1
    
    # +1 if: budget allows AND complex tier
    if budget_remaining > cost_per_builder * 2 and tier == "Complex":
        builders += 1
    
    return min(builders, 4)  # Cap at 4
```

**Test parallelization** mandatory for Standard+ (sharding by task dependency graph).

## Cross-Cutting Decisions Documented

| Decision | Rationale | Revisit Trigger |
|----------|-----------|-----------------|
| **No raw provider selection** - capability-based routing | Prevents decision paralysis, enables optimization | New capability not in registry |
| **Progressive memory enhancement** - markdown fallback always | No hard deps, user mental model preserved | Team > 3 OR sessions > 200 |
| **Tier-appropriate verification** - not "testing" for Tiny | Matches user skill + project type | Tiny project requests full test suite |
| **Adaptive Build Swarm** - ROI model not fixed count | Economics-aware, language-aware | Build time not improving |
| **3-Tier AI providers** - Default/Opt-In/Enterprise | Security surface, cost control, user simplicity | New provider beats default on capability+cost |
| **Parallel incremental gates** - Tier-scaled | Velocity + security both served | Gate becomes bottleneck |
| **Guided Tier Interview** - Interviewer-led not form | Non-technical users can't self-assess | User study shows confusion |
| **Platform rollout demand-gated** - 3 requests minimum | Prevents maintenance burden | Sustained demand for new platform |
