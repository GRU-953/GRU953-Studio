# GRU953-Studio — Full Audit, July 2026

**Audit date:** 2026-07-26 · **Version audited:** 4.5.0 · **Commit:** `0817432`

---

## 1. What this is, in five sentences

GRU953-Studio promises that a person who cannot write code can describe an app,
answer a few questions, and get a real, tested, safely-published result. That
promise rests on a set of automatic safety checks — for leaked passwords, for
licence problems, for "is this task genuinely finished?" — that run before
anything is committed or published. This audit examined every one of those
checks, every specialist role, every skill, every script and every published
claim, and it ran them rather than reading them. All of the checks currently
report success. Several of them report success **without having looked**, and
that is the main finding of this audit.

Nothing in this document is a guess. Every finding below was either reproduced by
running the code, or is a direct quotation of the line responsible. Where a
suspicion did not survive testing, it is recorded as withdrawn rather than
quietly dropped.

## 3. The four that matter most

### 3.1 The "is it really finished?" check accepts proof that it failed

**What the product promises.** A task is only marked *done* when a real command
was run to prove it, and the evidence is recorded. A separate check refuses to let
work past a checkpoint if any *done* task lacks that evidence.

**What actually happens.** The check accepts evidence that explicitly records
failure. Given a task whose recorded proof is a test run that exited with an error
code and reported three failing tests, the check replies:

```
{ "status": "clean", "reason": "every \"done\" row has a verified: cell" }
exit code 0
```

**How this was proved.** A minimal project was created with one task marked
*done*, whose evidence field was
`{"taskId":"T1","criterion":"tests pass","command":"npm test","exitCode":1,"stdout":"3 failing"}`.
The gate returned `clean`. The cause: the pattern that recognises structured
evidence accepts *any* exit code, and the separate contradiction-detector looks
for the words "exit" followed by a space and a digit — which the text
`"exitCode":1` never matches.

**What it means for you.** The one mechanism that guarantees "done means proven"
can be satisfied by proof of the opposite. Every other claim of completion in the
product ultimately rests on this check, so it is the first thing fixed.

**What we will change.** Require the recorded exit code to be zero, and teach the
contradiction-detector the structured form as well. A test that fails on today's
code and passes afterwards ships in the same change.

### 3.2 The licence check never looks

**What the product promises.** Before anything is published, the licences of all
borrowed code are checked, so you are not accidentally shipping something you
have no right to ship. It is one of five checks required before every commit.

**What actually happens.** Run against this very repository, it answers:

```
{ "status": "clean", "reason": "no recognised dependency manifests found" }
```

**How this was proved.** By running it. This repository contains four dependency
manifests and a lockfile listing ninety-three resolved third-party packages
(including express, hono, zod and ajv). The check inspects only the very top
folder and does not look inside subfolders, so it finds nothing and reports
success.

**What it means for you.** The check is not weak here — it is empty. And it fails
hardest exactly where this product is heading: a phone app keeps its Android
dependencies in a subfolder, a website project keeps them in another. In all
those shapes, the licence check would have reported "all clear" having examined
nothing.

**What we will change.** Search subfolders properly (respecting ignore rules, with
a sensible depth limit), and have the automatic build refuse to accept a verdict
that is silent or unreadable. Deliberately scheduled last, because switching its
eyes on before the packaging clean-up would flood it with problems from
unfinished work.

### 3.3 On Windows, the self-consistency check collapses completely

**What the product promises.** The studio works on Windows, macOS and Linux, and
an integrity check confirms the product's own internals are coherent.

**What actually happens.** Windows and Linux mark the end of a line of text
differently. The integrity check's pattern for reading the small settings block at
the top of each file only recognises the Linux form. On a Windows copy of the
repository — the default for Windows users, and nothing in the project currently
prevents it — every one of the thirty-eight specialist roles and every skill is
reported as malformed.

**How this was proved.** The exact pattern from the source was run against a file
saved in the Windows convention: no match, so the file appears to have no settings
block at all. The same pattern with a two-character change matches correctly.

**What it means for you.** The check that is supposed to prove the product is
internally sound is the check most likely to be broken on the most common desktop
operating system. And because the automatic build only ever runs on Linux, nobody
would find out.

**What we will change.** Make every text reader tolerant of all three line
conventions and of the invisible marker bytes some Windows editors add; pin the
repository's own line endings so the situation cannot arise here; and run the
whole check suite on Windows, macOS and Linux, plus a job that deliberately
creates a Windows-style copy and proves the checks still pass.

### 3.4 Two of the password-scanner's defences are dead code

**What the product promises.** Before any push, files are scanned for leaked
passwords and keys, including attempts to hide them by compressing or re-encoding
the text.

**What actually happens.** Neither of those two defences runs. The compression
branch uses a way of loading code that is not available in this kind of file, so
it throws an error the moment it is reached. Three of the four text encodings it
tries are not real encodings, so they throw too. Every one of these errors is
caught and silently discarded, so the scanner finishes and reports success.

**How this was proved.** By execution. Loading the compression library in this
file type raises `ReferenceError: require is not defined`. Three of the four
encodings raise `Unknown encoding`. Additionally, the one valid re-encoding always
passes the scanner's "is this readable text?" test even for ordinary text, so
every line is scanned twice and any finding from the second pass reports a line
number that means nothing.

**Correction — this entry initially understated the problem.** Fixing the way the
compression library is loaded turned out **not** to be sufficient. A compressed
file contains the same kind of bytes as an image, and the scanner skips those
before it attempts any decoding — so the compression branch could never be
reached, whatever way the library was loaded. Verified: with the loading fixed
and nothing else changed, a compressed file holding a real access key still
passed with "allow". Making the defence genuinely work required handling
compressed content *before* the skip, which is what was done. Recorded here
rather than quietly widened, because the first diagnosis was incomplete.

**What it means for you.** The plain-text scanning — which is what catches real,
honest mistakes — does work, and that is the case the security policy claims to
cover. But two advertised extra layers did nothing.

**What was changed.** Compressed content is now detected by its file signature
and scanned after unpacking, attributed to the containing file: a compressed
access key is now correctly refused, while an ordinary image with no secret is
still allowed, so nothing new is falsely flagged. The three invalid encodings are
gone, and re-encoded text is only attempted when the file actually announces
itself as such with a byte-order mark — which removes the double scan and the
meaningless line numbers with it. The scanner's honest scope — "protects against
mistakes, not sabotage" — stays exactly as stated.

**Second correction, found during a further pass.** The fix above only applied
to ordinarily-sized files. A file whose *compressed* size itself exceeds the
scanner's 4 MB threshold takes a different path — one that streams raw bytes
looking for plain text and never attempts decompression — so a secret packed
into a large compressed file was still invisible. Proved by building a
deliberately incompressible 5 MB payload so the compressed output itself passed
4 MB: it shipped with "allow". Fixed the same way, with one extra safeguard —
the amount the check is willing to decompress is capped, so a tiny file crafted
to explode to gigabytes when unpacked (a "decompression bomb") cannot exhaust
memory; it is simply treated as out of scope, the same honest limit already
declared for other unusual cases. Checked: a 200 MB bomb packed into a few
hundred kilobytes returned in about two seconds, with no crash. The first
attempt at this second fix was itself too strict — it capped the unpacked size at
the same 4 MB, which silently missed the realistic case of an ordinary large
file that legitimately unpacks to more than that. Corrected before landing.

### 4.1 A further pass, before stage 2 began

After stage 1 was pushed, a second, independent read was made of every check
this document had not yet closely examined — deliberately hunting for the same
*kinds* of problem the findings above describe, in the files a first pass
naturally spends less time on. Five more genuine defects turned up, every one
reproduced by execution before it was touched, and every fix again arrived with
a test proven to fail beforehand and pass after.

| # | Finding | Where | Proof |
|:--|:--|:--|:--|
| 35 | The Definition-of-Done check and the requirements-tracing check both carry the *exact same* pattern finding 1 fixed elsewhere — and neither had been updated. Both recognised the phrase "exit 1" but not the far more natural "exit code 1", so a row marked Pass/Met whose own evidence documented a failing test run was accepted as clean in both checks | `quality-gate.mjs:88`, `traceability-check.mjs:54` | Reproduced |
| 36 | The npm licence check silently examines **zero packages** for an older-style lockfile (the kind produced by npm 5/6), while still reporting a full pass. A real copyleft-licensed dependency recorded that way is invisible to the check | `licence-scan.mjs:113-131` | Reproduced |
| 37 | The Dart/Flutter licence check drops every package sourced from somewhere other than the official package registry (a forked package, a private plugin — both ordinary in real projects) before it looks at anything, yet still reports the whole ecosystem as checked | `licence-scan.mjs:251,280` | Reproduced |
| 38 | The knowledge-graph consistency check can be fooled by an ordinary sentence. It was supposed to only recognise a node as "defined" inside the graph's own `## Nodes` section, but it actually accepted a match anywhere in the file — so a stray mention like "task T1 was covered earlier" in an unrelated note silently counted as defining T1, hiding a genuinely broken reference | `memory-integrity.mjs:107-111` | Reproduced |
| 39 | The command that manually checks for and applies an update can leave a real file with literal, unresolved merge-conflict markers in it while reporting success. The underlying git command exits successfully even when its *last* step (restoring paused work) collides with an incoming change — a distinction the code did not check for | `auto-update.mjs:38-46` | Reproduced |

**Finding 39 is worth explaining in plain terms**, because it is the most
serious of the five and the least obvious. The update command does two things
in one step: it fetches the newest version, and it restores any of your own
unsaved changes on top afterwards. The fetch part can succeed cleanly while the
restore part collides — for instance, if you had started editing the very line
that also changed upstream. When that happens, the tool used to say "applied
successfully" regardless, while the file itself was left holding both versions
side by side with `<<<<<<<` / `=======` / `>>>>>>>` markers around them — text
that looks like an error message but is not one, and is easy to miss. The fix
checks, in a way that does not depend on English wording (so it also works
correctly for a user whose computer is set to a different display language),
whether any file was actually left in that state, and only then does it say
so plainly, name the file, and explain the two ways to resolve it.

None of these five change the wave plan — they are additional instances of
defect classes 1 and 4 already scheduled there, found and closed in the same
sitting rather than left for later. Full suite after all five: 225 tests,
225 pass.

### 4.2 Stage 2 — resolutions, and one finding narrowed after checking it precisely

Stage 2's job was cross-OS parity. Findings 3, 8 and 9 are now fixed, each with
a reproduction and a test proven to fail before and pass after:

- **Finding 3** (the licence check exits silently on Windows) — the entry guard
  compared raw file-path strings. It also turned out to fail the same way for
  a much more mundane reason this sandbox *could* reproduce directly: Node
  resolves a symlink when it loads the running script, but leaves the
  command-line path exactly as typed — so invoking the check through a
  symlink, with no special operating system involved, silently produced no
  output at all. Fixed by comparing the real, resolved location of both sides
  instead of the raw text.
- **Finding 8** (Windows can't launch `pip-licenses`, `dart`, `cargo`) — these
  are launched directly, without a command shell, and a shell is what
  normally finds a program installed as a `.cmd`/`.bat` wrapper (how several
  installers register a tool on Windows). The check now looks up the exact
  program file itself first.
- **Finding 9** (Windows fails every role and skill at once) — fixed by making
  the check tolerant of both ways a line can end, confirmed by re-encoding a
  full copy of this repository the way a Windows checkout would and running
  the check against it: all 38 roles and 35 skills were still recognised.

**Finding 26 turned out to be narrower than first described, and the register
is corrected rather than left overstated.** It was written as "no file reader
handles the invisible marker bytes." Checking each file precisely: two of them
— the dashboard and the knowledge-graph consistency check — genuinely did not,
and each was proven wrong by execution (a real project name vanishing from the
dashboard; a genuine broken reference being missed). The other four files
already tolerated those marker bytes, purely by chance: the pattern they use to
recognise a table row happens to treat those bytes as ordinary blank space, a
quirk of how the underlying text-matching language defines "blank." All six
were still given the same explicit, intentional handling, so correctness no
longer rests on that quirk continuing to hold if the pattern is ever tightened
— but only two of the six are recorded as a fixed bug; the other four are
recorded as deliberate hardening against a coincidence, which is a different
and more honest claim.

Finding 33's wording was corrected: the Windows assumption was real for one
narrow case (autonomous cloud sandboxes, which genuinely are usually
Linux-based) but was stated as if it applied to the whole guide, which
contradicted the cross-platform work above it. Reworded to scope the
assumption to that one case and point at where the studio's own tooling is
proven cross-platform instead.

Full suite after stage 2: 236 tests, 236 pass.

### 4.3 Two more, found only because the Windows CI leg itself ran and failed

This is the point of building the matrix in the first place: the first real
run of the `windows-latest` leg failed with 2 of 236 tests red, both genuinely
new — neither is a repeat of findings 3/8/9/26 above, and neither could be
reproduced on this Linux sandbox directly (each is explained below, with what
*could* be checked here instead).

- **A quoted Windows path silently lost every backslash before the
  confirm-script exemption ever saw it (`gate.mjs`/`scan.mjs`,
  `lib.mjs:normalizeForPushCheck`).** A step written in an earlier round to
  defeat an obfuscated push (`p\ush` → `push`, unescaping a backslash before
  *any* character) was commented "outside quotes" but was never actually
  quote-aware — it ran across the whole command string regardless of quoting.
  A genuine Windows path passed as a quoted argument, exactly what
  `node "D:\a\...\confirm-publish.mjs" "D:\a\..."` looks like, had every
  backslash in it stripped before `path.basename()` downstream ever ran,
  corrupting the path into one run-on word so the confirm-script exemption no
  longer recognised its own filename — reintroducing the exact deadlock that
  exemption exists to prevent (gate.mjs denying the one command that records a
  publish confirmation), but only on Windows. Reproduced directly: the
  windows-latest leg's log shows `not ok 13`, `'deny' !== 'allow'`. Fixed by
  making the un-escape step actually quote-aware — outside any quotes it still
  unescapes `\X` → `X` unconditionally (the original obfuscation case stays
  caught); inside double quotes it now only unescapes bash's own four
  recognised escapes (`\$`, `` \` ``, `\"`, `\\`); inside single quotes nothing
  is unescaped at all, matching real bash. This does not reopen the
  obfuscation case the line was written for, because that case is unquoted;
  real bash does not unescape `"-\-public"` either, since double quotes never
  touch `\-`. The string-transform half of the fix is covered by a new
  platform-independent unit test; the `path.basename` half can only be proven
  by the windows-latest leg itself passing, which it now does.
- **An auto-update test asserted exact file bytes without pinning the git
  config that decides them (`hooks.test.mjs`, the auto-update fast-forward
  test).** The test runs the real `auto-update.mjs` script as a plain child
  process, deliberately without this suite's own hermetic git environment
  (auto-update.mjs is the production script; it must behave correctly under
  whatever git config a real user's machine has, not just this suite's
  pinned one). GitHub's `windows-latest` runners set `core.autocrlf=true` in
  system git config, so the script's own `git pull` rewrote the fixture's
  `\n` line endings to `\r\n` on checkout — ordinary, correct git behaviour,
  not a defect in auto-update.mjs. The test's assertion just never accounted
  for it. Reproduced directly: the leg's log shows `not ok 119`, expected
  `'hello\nupdate\n'`, actual `'hello\r\nupdate\r\n'`. Fixed by pinning the
  test repository's own local `core.autocrlf` to `false` (a local git config
  always wins over system/global), the same way every other fixture in this
  suite already does via `initRepo()` — making the fixture's line endings the
  thing under test, rather than an artifact of whichever runner happens to run
  it.

Full suite after this fix: 237 tests, 237 pass (one new regression test
added for the first finding). Both are genuinely platform-shaped bugs of
exactly the kind this stage's CI matrix was built to surface — findings that
would otherwise have shipped invisibly, silently reintroducing a real deadlock
for any confirm-script invocation using a quoted Windows path.

### 4.4 A further pass, before stage 3 began

Two background review agents were set loose on the files this audit had not
yet closely examined — the four confirmation scripts, the role-count check,
the self-heal nudge, the status-line renderer, and every sibling of the
quote-handling code the Windows fix above had just touched — with instructions
to find nothing if there was nothing, rather than invent minor nitpicks. Two
genuine, reproduced bugs came back, both fixed; a further three were found,
investigated, and — after one was actually attempted and found to make things
worse — deliberately left as disclosed limitations rather than rushed.

**Fixed, both reproduced by execution first:**

- **All four confirmation scripts** (`confirm-checkpoint.mjs`,
  `confirm-go-public.mjs`, `confirm-memory-persist.mjs`,
  `confirm-publish.mjs`) **wrote their approval record with no error
  handling at all.** Reproduced: putting a folder where the record file
  should be (plausible from a stray step, a bad merge, or a case-folding
  quirk on Windows or a Mac) made every one of them crash with a full,
  technical internal error message and no explanation — the exact thing this
  project otherwise always avoids showing a non-technical user. All four now
  share one small, centralised routine (`writeConfirmationRecordOrExit` in
  `lib.mjs`) that turns that same failure into a plain sentence: what went
  wrong, and what to check. A read-only folder or a full disk would have
  failed exactly the same way; both are covered by the same fix.
- **`roster-check.mjs` read its most recent decision record (`:117`) without
  any error handling**, unlike every other file-read in that same script.
  Reproduced: replacing that record with a folder produced the same kind of
  internal, technical crash instead of the check's own plain-English "here's
  what's wrong" message. Fixed to match the rest of the file.

**Found, and left as disclosed limitations rather than fixed (all three are
"the check may occasionally refuse something harmless," never "the check may
miss something real" — the safe side of the two possible mistakes, matching
this file's own stated approach throughout):**

- A rare punctuation pattern (a comma inside curly braces, mimicking a shell
  shorthand for "either of these words" — `lib.mjs:960`/`961`) is recognised
  even when it's sitting inside quotes, where it's inert. **A fix was
  actually written and tried**, scoped so it could only ever make the check
  more lenient inside quotes, never less strict elsewhere — and it broke an
  existing, deliberately tricky test in `hooks.test.mjs` one line below where
  this pattern was first hardened (the `{g""it,pu""sh}` case), because that
  test's exact scenario turns out to be a case where the punctuation
  genuinely IS live even though part of it sits next to a quote mark (real
  command-line rules resolve this kind of shorthand *before* removing
  quotes, so a quote mark part-way through doesn't neutralise it the way it
  looks like it should). Getting that distinction right calls for exactly the
  kind of careful, narrow work the rest of this audit has insisted on, not
  something to rush through in the same sitting it was found in — so the
  attempt was undone, confirmed back to passing (238/238), and left here as a
  named, open item instead.
- A specific placeholder text (`$IFS`, a technical stand-in for "any
  whitespace" — `lib.mjs:1026`) is treated as significant even inside single
  quotes, where real command-line rules say it should not be. Rare in
  practice, and the same safe-side mistake as above.
- An apostrophe inside a properly quoted phrase (a possessive, a
  contraction — "it's", "the user's") can be silently dropped from the
  check's internal working copy of the text (`lib.mjs:1036`-`1037`).
  Confirmed this never changes the check's actual yes/no answer in every
  case tried; it only affects a copy of the text nothing else ever sees.

Full suite after this further pass: 238 tests, 238 pass.

### 4.5 A systematic sweep, before stage 3 began — four background agents, ten confirmed bugs, all fixed

A direct re-read first caught one small but real drift issue on its own:
`.gitattributes`'s own comment claimed "the CI job that deliberately builds a
CRLF working tree overrides this after checkout" — no such job has ever
existed in `.github/workflows/ci.yml`. The genuine coverage comes from two
other places instead: a test in `hooks.test.mjs` that re-encodes a throwaway
copy of the repository to CRLF, and the real `windows-latest` leg itself
(exactly what caught the two findings in section 4.3). The comment is now
corrected to say so.

Rather than more spot-checks, four background review agents were each given a
small group of the remaining hook files — the ones no earlier pass had gone
over closely — with the same brief: read every line, reproduce anything
suspicious by actually running it, and say plainly if nothing was found rather
than inventing a minor nitpick. Between them they returned ten genuine,
reproduced findings. All ten are fixed below, each with a test proven to fail
first and pass after; one further issue was investigated and is recorded as a
disclosed, open limitation rather than a rushed fix.

**The two most serious, both in the secret/push-safety checks:**

- **A key-file name check was case-sensitive with no reason given for it**
  (`scan.mjs:347`, the check for `.env`/`id_rsa`/`.pem`/`.key` style
  filenames). Its neighbour two lines below has an explicit comment
  explaining why IT is deliberately case-sensitive; this one had no such
  note, because it wasn't deliberate. Reproduced: a file named `.ENV`,
  `Secrets.ENV` or `Server.PEM` — all ordinary, legal names on every
  operating system this project targets — was invisible to the filename
  check. This mattered more than it might sound: the *content* check for
  secrets requires a quoted value, but real `.env` files conventionally use
  **unquoted** `KEY=value` lines, which the content check doesn't catch
  either — so a mis-cased `.env` file was a real, working way for an
  ordinary secret to ship unnoticed. Fixed by matching the filename
  case-insensitively, the same as every other filename-shaped check in this
  project.
- **The opt-in "keep my private notes across sessions" permission had two
  separate copies of its expiry check, and only one of them had been
  fixed.** `gate.mjs` already closed finding 12 (an expired permission
  being revived by an unrelated fresh timestamp elsewhere in the same file)
  for the *push* decision. `scan.mjs` turned out to have kept its own,
  separate, never-updated copy of the same check for a related but
  different decision (whether the private-notes folder is exempted from the
  "these files never leave your machine" rule). Reproduced: a permission
  record whose real approval was three hours past its one-hour limit was
  still honoured, because an unrelated fresh timestamp elsewhere in the same
  file satisfied the unfixed check. Fixed by making both checks share
  exactly one implementation, so the two cannot drift apart like this
  again.

**Two more that would have shown a wrong answer, though not a dangerous one:**

- **The command-centre summary could say "No tasks yet" while the table
  directly beneath it listed real, active tasks** (`dashboard.mjs`). The
  summary's own code comment says any status word it doesn't recognise
  should still be shown, counted as "Other" — but the list of things it
  actually displays never included an "Other" entry, so those rows were
  silently invisible in the summary while still appearing in the table.
  Confirmed the worst case: a status column not spelled exactly "Status"
  put every row into this same invisible bucket, rendering the whole
  summary as if the project had no tasks at all. Fixed to show the group it
  was always supposed to show.
- **A completely healthy project-memory record could be wrongly flagged as
  broken, purely because a link between two notes was written as an
  ordinary English sentence** (`memory-integrity.mjs`). A line like
  "- T1 implements R1." (note the full stop) had its full stop swept up as
  part of the reference itself, so the check looked for a note literally
  named "R1." — which of course doesn't exist — and reported a broken link
  that was never really broken. Fixed by trimming ordinary sentence
  punctuation from a reference before checking it.

**One licence-check gap of the same shape already found and fixed twice
before, in a project type nobody had checked yet:**

- **A project using only Pipenv (`Pipfile`/`Pipfile.lock`, the standard
  Python dependency manager, but no `requirements.txt` or `pyproject.toml`)
  was invisible to the licence check** — not even reported as "not checked",
  just silently absent, worse than every other unchecked case in this file.
  The irony: the code to *read* a Pipenv lockfile was already sitting right
  there, unreachable, because the earlier gate that decides "is this a
  Python project at all" never looked for Pipenv's own files. Fixed by
  recognising them.

**Three still-open items completed from an earlier finding, not new bugs of

plain sentence") named seven specific unguarded reads/writes across six
files. Five of the seven — the four private-notes-approval scripts and the
role-count check — were fixed in the pass just before this one. The remaining
two, `verify-progress.mjs`'s own record read and `dashboard.mjs`'s own
rendered-page write, are fixed now, using the exact same approach. **Finding
21 is therefore now fully resolved**, three stages ahead of where it was
originally scheduled (stage 3) — stage 3's remaining scope is genuinely
smaller than planned: findings 22 (races between checking a file exists and
reading it) and 23 (the update checker's English-only, developer-only
assumptions) only.

**One further issue investigated and left as a disclosed limitation, not
fixed:** the licence check's Python fallback trusts whatever program named
`pip-licenses` it happens to find on the system search path, with no check
that it belongs to this particular project's own isolated Python environment
(a "virtual environment", in Python's terminology). A different, unrelated
copy of that program being reachable could report on the wrong environment
entirely, missing a real problem while still saying "checked". Properly
fixing this means teaching the check to recognise and prefer a project's own
virtual environment first — genuinely new logic, not a small correction, and
one that needs its own careful cross-platform testing rather than a rushed

than either silently skipped or hastily patched.

## Stage 3 — every failure produces a clear sentence, never a crash report

Finding 21 was already fully resolved in section 4.5, ahead of schedule.
Stage 3's real remaining work was findings 22 and 23 — both now fixed, each
with a test proven to fail first and pass after.

**Finding 22 — a check crashes if the thing it's checking disappears
mid-check.** Five of this project's own gates — content-check, quality-gate,
memory-integrity, dashboard, and (not originally named in the finding, found
while fixing the other four) traceability-check — each opened with the same
two-step check: "does this folder exist, and separately, is it really a
folder". Between those two separate questions there is a gap — however
brief — in which the answer to the first question can stop being true: the
folder could be deleted, replaced, or renamed. When that happened, the
second question crashed with a full technical error message instead of this
project's own plain, one-sentence explanation. All five now ask a single
question instead of two, the same safe approach a sixth check in the same
file already used correctly — closing the gap rather than merely narrowing
it. A genuine timing accident like this can't be manufactured on demand in
an automatic test, so what's proven instead is the property that actually
matters: the new single check never crashes, for any input tried, and still
correctly tells a missing folder from a file from a real folder.

**Finding 23 — the update checker only worked in English, and only for a
developer's own checkout.** Two separate problems, both fixed:

- **Only worked in English.** Checking whether an update was available
  looked for the literal English words "Your branch is behind" in git's own
  output — but git translates that exact message into whatever language its
  own settings request, so this silently did nothing for anyone running git
  in another language. (This precise mistranslation could not be reproduced
  directly in this sandbox — no git language packs are installed here — but
  git translating its own messages this way is well-documented and not in
  question.) Replaced with a check that asks git directly, in a form that
  is a plain number in every language: "how many commits behind am I?".
  Confirmed by direct testing that this number-only answer does not change
  under a foreign-language setting, a blank one, or a nonsense one — the
  actual property the fix depends on.
- **Only worked for a developer's own checkout.** The updater guessed its
  own location by assuming it always sits at one fixed, exact depth inside
  its own folder structure — true for this project's own layout today, but
  not guaranteed for every way the plugin might come to be installed.
  Replaced with the same safe approach this project's own project-detection
  logic already uses elsewhere: look upward, one folder at a time, for the
  actual marker being searched for, rather than assuming how far up it must
  be. Proven directly: the updater now finds and applies a real update even
  when deliberately placed at a different depth than usual, which the old,
  fixed-depth guess could not have done.

Full suite after stage 3: 252 tests, 252 pass.

### Why none of this was caught

The automatic build is a single job on Linux with one version of Node. Nothing in
the three client bridges is built, checked or tested. The protocol server is never

## Stage 7 — the licence gate that actually looks, then release 5.0.0

**Finding 2 — the licence gate finally looks past the top folder.** This is
the finding this whole document opened with: `main()` checked only the exact
directory it was given, so it reported *"no recognised dependency manifests
found"* on this very repository, which holds real manifests one folder down

same "close the concrete case found, not a general grammar engine"
discipline this project already applies to its push-safety matcher and its
documentation checks. It skips each ecosystem's own dependency tree

this repository right now, it finds all three real `clients/` manifests and

saying "no manifests found".

**A second, smaller bug found in the same sitting.** Running the fixed
scanner against this repo's own real npm packages for the first time
surfaced a genuine false alarm: a package licensed `(MIT OR CC0-1.0)` — a

*whole string* against a flat allow-list, never parsing it as an expression
the way this file's own SPDX parser already does for Dart, Cargo and Maven.

identical piece of licence text gets the same answer regardless of which
ecosystem it came from. Proven with a genuine control: a package licensed

permissive choice), while `(GPL-3.0-only OR AGPL-3.0-only)` — where neither
option is — still blocks.

## 8. Honest limits of this audit

- **Two suspicions were investigated and withdrawn.** First, the approval-file
  timestamp was thought to break on Windows line endings; testing showed the
  pattern used matches both conventions correctly. Second, one hook event name
  and two tool names were thought to be invalid; checking the official
  documentation showed all three are real. Both are recorded because a false
  alarm in a security audit costs as much trust as a missed problem. (The first
  investigation did uncover a genuine nearby problem — finding 12.)
- **No Windows or macOS machine was available.** The Windows findings were proved
  by running the exact patterns and path logic against Windows-shaped input, not
  on Windows itself. Stage 2 replaces that inference with a real build on all
  three systems — which is the point of doing it early.
- **This was not a penetration test and not a fuzzing campaign.** It is a
  systematic read-and-run audit. Deliberate attack resistance is out of scope,
  consistent with the product's stated security posture.
- **No existing user projects were examined** — only the product itself.
- **The audit is a snapshot** of commit `0817432`. Anything merged afterwards is
  not covered.
- **One row of §9's own verification table was not performed.** Stage 7's

  end — needs a live, interactive Claude Code session with a real
